# Jev Filter — рабочее состояние (iQOO 15R / Android 16)

## Иконка у копии уведомления (проверено 10 октября)

Симптом от пользователя: «приходят уведомления от других приложений с иконкой от Jev». Это наши
копии: в режимах «отложить» и «сначала тихо» оригинал снимается и выкладывается заново от имени
`com.jevfilter`, поэтому система считает уведомление нашим.

Что выяснилось:
- `dumpsys notification --noredact` показывает у копии `icon=Icon(typ=RESOURCE pkg=com.jevfilter id=0x7f020001)` —
  это `smallIcon`, который мы ставим.
- **В шторке этот `smallIcon` не рисуется.** Ром (OriginOS) показывает значок приложения-отправителя
  (launcher icon). Проверено сравнением снимков: с нашим `ic_small` и с `Icon.createWithResource(pkg, ai.icon)`
  от приложения-источника шторка выглядит одинаково — колокольчик Jev.
- Гипотеза «это из-за targetSdk ≥ 31» проверена сборкой с `-TargetSdk 30`: иконка та же, гипотеза неверна.
- Иконок уведомлений в статус-баре у этого рома нет вообще (включены только системные: луна, BT, VPN,
  VoLTE, скорость, сеть), поэтому подмена `smallIcon` на телефоне визуально не видна — но она честная:
  на стоковом Android и в сторонних слушателях (watch-бриджи) значок будет от приложения-источника.
- Свой API для возврата: `snoozeNotification(key, ms)` есть, `unsnoozeNotification` **нет**. Значит
  «спрятать и вернуть оригинал» невозможно: спрятать можно только снятием, а снятое чужое уведомление
  вернуть нельзя — отсюда копия. (Отложенное системой уведомление снимается иначе: снуз убирает запись
  из `mNotificationsByKey`, поэтому `cancelNotification` по нему уже не сработает — спам вернулся бы
  по истечении снуза. Этот путь отвергнут.)

Вывод для пользователя: родная иконка и имя возможны только в режиме «убирать лишнее», где одобренные
уведомления не трогаются вовсе. Цена — спам успевает пискнуть за 1–3 с, пока идёт решение.

**Решение (10 октября): переключились на «убирать лишнее».** Проверено генератором: одобренное
уведомление остаётся родным (`0|com.jev.spamgen|104|keep2` — владелец исходное приложение, копий
`com.jevfilter` нет вообще), реклама снимается, в журнале `REMOVE dismiss 1.00` и `LEAVE keep 0.97`
без пометки «(отложено)».

Проверено и на стороннем генераторе фейковых уведомлений (`zopsoft.com.zerofall`, «Notifications»):
он ставит в уведомление `smallIcon = drawable/face` (свой PNG с логотипом Facebook) и `color = 0xff3b5998`,
`contentView` пустой, — а ром в шторке рисует его собственный значок приложения (бирюзовый
колокольчик из `drawable/logo.png`). То есть чужая иконка не показывается даже у приложения,
которое специально для этого сделано: его выбор иконки живёт только в его превью.

## Баг «снимает только первое уведомление» (найден и исправлен 2 октября)
Симптом: из нескольких уведомлений подряд снималось только первое, следующее оставалось, а при
третьем пропадало предыдущее.
Причина: защита от повторов сравнивала **ключ** уведомления в окне 60 секунд. Приложения (Ozon:
`id=5, tag=null`) переиспользуют один ключ для каждого нового уведомления, поэтому каждое
следующее считалось «повтором» и пропускалось. Когда окно истекало, обрабатывалось очередное —
и снимало то, что висело в тот момент.
Доказательство (журнал): `REMOVE ... первое:` затем `SKIP повтор (то же уведомление)` на втором,
и три живых `SKIP повтор` на настоящих уведомлениях Ozon.
Исправление: дедупликация по **содержимому** (пакет + ключ + заголовок + текст) с окном 3 секунды
(`Pipeline`, поля `lastFingerprint`/`lastFingerprintAt`). По ключу дедуплицировать нельзя.
Проверка: три уведомления с одним ключом и разными текстами — сняты все три, шторка пуста.

## Баг «журнал засоряется уведомлением VPN» (найден и исправлен 2 октября)
Симптом: журнал решений забит строками `SKIP постоянное [com.github.metacubex.clash.meta] Сервер`,
обновление раз в секунду, настоящие решения вытесняются.
Причина: VPN (Clash Meta) перевыкладывает своё постоянное foreground-уведомление со счётчиком
трафика ~1 раз в секунду, ключ всегда один (`0|com.github.metacubex.clash.meta|2131296585|null|10378`,
флаги `ONGOING_EVENT|FOREGROUND_SERVICE`). Само решение верное (постоянные уведомления
пропускаются), но **каждое событие писало строку**: 721 из 813 строк журнала (89 %) — от VPN.
Кольцо на 600 строк вытесняло реальные решения примерно за 10 минут — это и был настоящий вред.
Исправление: `JeLog.addThrottled(c, throttleKey, windowMs, line)` + `Pipeline.quiet(...)`,
окно `CHATTER_MS = 5 мин`. Все 8 «пустых» веток (пустое, групповое, сводка группы, постоянное,
служебное, `MISS не в списке`, устарело, повтор) идут через троттлинг; **решения (REMOVE/LEAVE) —
нет, они пишутся сразу**. Первое событие пишется сразу, повторы считаются молча, следующая запись
после окна показывает их число: `(+N таких же за 5 мин)` — факт не теряется, шум уходит.
Ключ троттлинга — пакет + ключ уведомления, а не приложение: иначе схлопнулись бы разные сообщения
одного мессенджера (та же ловушка, что в баге с Ozon выше).
Проверка: за 5 минут болтовни VPN (~300 событий) — 2 строки вместо ~300; три тестовых
уведомления в тот же момент дали `REMOVE`/`REMOVE`/`LEAVE keep 0.96` сразу, без задержки.

## Журнал решений отдельной страницей (сделано 3 октября)
`JournalActivity` — отдельный экран: список во всю высоту, прокрутка, иконки приложений.
- `JeLog` теперь хранит не строки, а `Entry` (время, вид, пакет, `note`, `body`, `raw`) —
  разбор своей же строки формата `REMOVE dismiss 1.00 [pkg] заголовок :: текст`. Файл
  `files/jev.log` пишется как раньше, поэтому проверки через adb не изменились.
- Кольцо в памяти увеличено с 600 до 1500 записей.
- Строка списка: цветная черта слева (красная — снято, зелёная — оставлено, серая — пропущено,
  синяя — не в списке), иконка, название приложения, текст уведомления, слово вердикта и
  справа моноширинно уверенность/причина. Дни разделяются подписями «сегодня»/«вчера»/«2 октября».
- Вкладки «Всё» / «Только решения» (выбор запоминается), действия «Скопировать» и «Очистить».
- Главный экран: вместо встроенного мелкого текста — счётчик («N записей, из них решений M,
  последнее — …») и кнопка «Открыть журнал».

Две ошибки, найденные проверкой на телефоне (обе исправлены):
1. разбор файла при старте: отметка времени `MM-dd HH:mm:ss` — это 14 знаков, а не 13, из-за чего
   после перезапуска страница оставалась почти пустой (на экране было видно «2 записей» вместо 13);
2. смена вкладки не перерисовывала список: `reload()` выходил по «версия журнала не изменилась»,
   хотя фильтр меняет содержимое, а не версию — теперь сравнивается и фильтр.

`SocketTimeoutException: Read timed out` и `SSLHandshakeException: connection closed` — это сеть,
а не приложение. Замеры **с телефона** через `curl`:
- POST /api/alpha/decisions: 2 успеха из 6 (1.6–2.2 с), остальные — 0 байт за ~10.18 с;
- GET /api/v1/models: 1 из 3, зависание тоже ровно ~10.18 с;
- контроль `api.ipify.org`: 3 из 3 успешно по тому же туннелю;
- внешний IP телефона: 78.17.19.21 (VPS в Амстердаме, VPN `moe.nb4a` включён).

Вывод: зависает участок **VPS → Cloudflare/openrouter.ai**, причём с фиксированным обрывом ~10 с.
Приложение это не лечит, только переживает повторами.
Что сделано в приложении: лестница попыток с таймаутами 4/8/8/8 с (короткая первая — оборванный
путь молчит и ждать его бессмысленно), пауза 400 мс, в журнале пишется «с N-й попытки, X с»,
при полном провале уведомление озвучивается (fail-open). Было: 2 попытки по 8 с ≈ 43% успеха.
Проверено: 9 из 9 тестовых решений с первой попытки (~2 с).
Что осталось: разобраться с маршрутизацией на VPS (xray/WARP) — участок VPS→OpenRouter.

- **silent** («сначала тихо», по умолчанию): показываем свою тихую копию, отменяем оригинал
  (отмена обрывает и звук), спрашиваем Джева. Одобрено → та же копия перевыкладывается на канале
  `jev_audible` (importance=4, со звуком). Спам → копия убирается. Ошибка/нет сети → копия
  озвучивается (fail-open).
- **remove** («убирать лишнее»): просто снимаем то, что Джев назвал спамом.

## Локальный стоп-лист (сделано 7 октября)

`StopList.java` решает часть уведомлений **до сети** и до любых действий с оригиналом.
Проверка стоит в `Pipeline.onPosted` сразу после чёрного списка: попал в стоп-лист → строка
`LEAVE стоп-лист (причина)` в журнале, оригинал не трогаем вовсе (значит, он и звучит как обычно),
запрос к Джеву не делается.

Что попадает в стоп-лист:
- банк, госуслуги/налоговая, системное — по `Prefs.riskNote(pkg)`: их уведомления не снимаются
  никогда, даже если пакет в чёрном списке (в списке есть и банковские приложения);
- слова: код подтверждения/доступа, одноразовый, пароль, пин-код, otp, one-time, verification,
  authenticat, 2fa, cvv, 3-d secure, «никогда никому», «не сообща»;
  деньги: списан, зачислен, перевод, баланс, платёж, операци, пополнен, снятие, задолженност,
  штраф, квитанц; безопасность: вход в, новое устройство, подозрительн, безопасност,
  заблокирован, мошенник, взлом; `подтвержд` (существительное — «подтверждение операции»);
- регулярка «слово код/code/pin/otp/пароль рядом с 4–8 цифрами»; слово должно стоять отдельно,
  поэтому «промокод 12345» и «код товара 4821» проходят мимо и уходят к Джеву;
- пустой или нечитаемый текст (на Android 15+ так выглядит OTP, у которого система вырезала
  содержимое).

Цифры сами по себе **не** повод оставить: в рекламе полно цен и промокодов. Если в тексте есть
4–8 цифр подряд, порог уверенности поднимается до `DIGIT_THRESHOLD = 0.75`, и в журнале видно
`цифры, порог 0.75`. В журнал текст стоп-листа пишется через `StopList.mask` (цифры → `•`).

`JevClient.mask` заменяет наружу любые последовательности из 4–8 цифр на `•`, сохраняя длину.

## Режим «отложить до решения» (сделано 7 октября)

`mode = defer` (теперь это режим по умолчанию, у пользователя тоже выставлен):
оригинал снимается сразу — отмена обрывает и звук, — а своей копии не показываем, пока Джев
думает. Оставил → показываем копию в канале `jev_audible` со звуком. Назвал спамом → не
показываем вовсе. Итог: спам не мелькает в шторке вообще, а одобренное появляется через 1–3 с.

Три режима переключаются нажатием на строку «Режим»: `defer` → `silent` → `remove`.
- `silent` — тихая копия видна сразу (прежнее поведение);
- `remove` — оригинал живёт до вердикта, снимается только спам.

Что может пойти не так и что сделано:
- **процесс убили между снятием и вердиктом** → `Pending.java` кладёт текст в `files/jev.pending`
  ДО снятия и удаляет после вердикта; `Pipeline.restorePending` возвращает оставшееся при первом
  `onListenerConnected` этого процесса (один раз за процесс, иначе повторная привязка слушателя
  возвращала бы ещё не решённое). Возврат идёт со звуком и без кнопок — PendingIntent через файл
  не передать;
- **`cancelNotification` ничего не возвращает** (отказ выглядит как успех) → перед возвратом
  копии и перед удалением спама проверяем `getActiveNotifications(new String[]{key})` и снимаем
  повторно;
- **нет ответа модели, нет сети, HTTP-ошибка, мусор в ответе** → уведомление показывается, а не
  пропадает: `showCopy(..., audible)` в ветке «нет сети», в `catch` и в проверке breaker'а,
  в журнале `LEAVE нет сети…` или `LEAVE (ошибка…)`. Пустой `choice` тоже даёт исключение, то есть
  тоже fail-open. Принцип: ошибка в сторону «показать» дешевле ошибки в сторону «спрятать»;
- **`notify()` отказал молча** (запрет своих уведомлений, лимит постов) → в режиме «сначала тихо»
  копия перед снятием оригинала проверяется через `NotificationManager.getActiveNotifications()`;
  не встала — оригинал **не** трогаем и пишем «копия не показалась, оригинал не трогаю». В режиме
  «отложить» не удалось показать одобренную копию — запись остаётся в защёлке и вернётся при
  следующем запуске;
- **не удалось записать защёлку** (`Pending.put` вернул false: нет места, ошибка ФС) → оригинал
  не снимаем вообще, работаем как `remove`;
- **свои уведомления запрещены** → режим вырождается в `remove`, в журнал пишется предупреждение.

## Чего сделать нельзя
`NotificationAssistantService` (перехват уведомления ДО звука) — это @SystemApi, его нет в
публичном `android.jar` (проверено `javap` + содержимое jar). Стороннее приложение не может
заглушить чужое уведомление до его появления. Поэтому используется связка «тихая копия + отмена
оригинала»: первые доли секунды звук может успеть начаться. Абсолютная тишина достигается только
выключением звука у каналов самих приложений (описано в экране «Инструкция»).

## Автосохранение списка
`AppPickerActivity.saveNow()` пишет копию чёрного списка в `files/blacklist.backup`.
Восстановление: `adb push bl.txt /data/local/tmp/` → `run-as com.jevfilter cp /data/local/tmp/bl.txt files/blacklist.backup`.

## Урок (потеря данных)
2 октября я перезаписал чёрный список пользователя (43 приложения) тестовым и **не сделал копию** —
настройки приложения не имеют резервных копий, восстановить было нечем. Правило: перед любой
правкой `shared_prefs/jev.xml` сначала сохранить текущее содержимое файла на компьютер.
Восстановлено 23 записи из 43.
Дополнение (2 октября): копию prefs снимать **байт-в-байт** — `cmd /c "adb ... exec-out
\"run-as com.jevfilter cat shared_prefs/jev.xml\" > файл"`. Через PowerShell `>` файл получается
UTF-16 (2470 байт → 4942). Имя файла prefs — `shared_prefs/jev.xml`, для сравнения размер 2470 байт.
Вторая засада: после `am force-stop` система успевает поднять процесс слушателя за 1–2 секунды и он
читает **старый** файл prefs; правка на диске при этом не подхватывается. Правильная
последовательность: `force-stop` → сразу `cp` нового файла → сразу `am start`.


## Что это
Своё Android-приложение вместо MacroDroid. Смотрит уведомления только тех приложений,
что перечислены в ЧЁРНОМ списке, спрашивает у Jev (TypeSafe System One) вердикт и снимает
**ровно это уведомление** по его key. Шторку целиком не чистит никогда.

## Файлы
- `jevfilter.apk` — собранный подписанный APK
- `app\` — исходники (AndroidManifest.xml, res/, java/com/jevfilter/)
  - `JevListenerService.java` — слушатель: чёрный список → Jev → cancelNotification(key)
  - `JevClient.java` — HTTP: 1 запрос + второй только если первый не дошёл; маскировка цифр
  - `Net.java` — проверка сети + предохранитель (3 неудачи → пауза 2 мин)
  - `StopList.java` — локальный стоп-лист: коды, деньги, безопасность, банк/госуслуги, до сети
  - `Pending.java` — защёлка `files/jev.pending` для режима «отложить до решения»
  - `Prefs.java` — списки по умолчанию, порог, «устарело через N секунд», riskNote(), режимы
  - `Ui.java` — визуальный язык: палитра, поля, кнопки, hairline, кольцо
  - `MainActivity.java` — главный экран (кольцо-состояние = выключатель), журнал
  - `AppPickerActivity.java` — выбор приложений с чекбоксами + предупреждение о банках
  - `JournalActivity.java` — журнал решений отдельной страницей (список, иконки, вкладки)
  - `JeLog.java` — кольцо записей в памяти (1500) + файл `files/jev.log` + троттлинг шума
  - `res/` — адаптивный значок (щит с галочкой), `res/values/colors.xml`
- `build.ps1` — сборка без Gradle (aapt2 compile/link + javac + d8 + zipalign + apksigner)
- `tools\jdk-17.0.20.1+1`, `sdk` — тулчейн
- `spamgen\` — тестовый генератор уведомлений (удалён с телефона)

## Что важно знать
1. **Слушатель привязывается системой не всегда сразу.** После переустановки помогло:
   `disallow_listener` → `force-stop` → запуск приложения → `allow_listener`.
   После перезагрузки телефона нужен автозапуск для Jev Filter (vivo/iQOO его любит блокировать).
2. **Уведомления от `com.android.shell` (uid 2000) системно нельзя снять** ни через слушателя,
   ни через MacroDroid. Это не баг приложения — тесты через `cmd notification post` для проверки
   самого снятия не годятся, нужен обычный app.
3. `dumpsys notification --noredact` содержит ещё и архив истории: проверять наличие уведомления
   надо только внутри секции `Notification List:`.
4. Jev вызывается через `POST https://openrouter.ai/api/alpha/decisions`, модель `typesafe/jev-1.13`,
   ~$0.00002 за уведомление.
